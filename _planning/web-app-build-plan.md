## Decisions made so far

- **Scope for now: web app only.** Discord bot (`discord/`) stays untouched — will be adapted to whatever infra we build later, not now.
- **Backend/frontend split kept separate from Discord bot.** No shared query engine between the Discord bot's `stats_query_engine.py` and the web app's backend. Avoids a risky refactor of a 3,142-line file; can revisit later if logic drifts.
- **Data layer: stay on CSVs for v1.** Keep reading `Ref/*_CompStats.csv` directly, same as the Discord bot and dashboard_site already do. Defer Postgres migration until something actually needs per-user state (e.g. auth/profiles, which is optional/deferred anyway).
- **Foundation: reuse dashboard_site's FastAPI backend, replace its frontend.** dashboard_site's API (`dashboard_site/api/`) is a working, generic query engine on real data — keep and extend it rather than rewriting. Its current frontend (`dashboard_site/web/` — plain HTML/JS, no build step) gets replaced with a real frontend, since the ask is "looks nice, minimal custom frontend code, smooth on mobile."
- **New frontend: Next.js (React/TypeScript) + a component library** (shadcn/ui or similar on Tailwind) rather than hand-rolled CSS — minimizes custom UI code and handles responsive/mobile well by default.
- **Backend views that need Weighted Rank should call `Models/League.py` directly**, not reimplement the min-max rating math inside `dashboard_site/api/query_engine.py`. Keeps one source of truth for that formula (DashApp already does this).

## Grounding findings

**Weighted Rank formula** — located in `Models/League.py:83-142` (`get_totals_df` / `get_avg_df`): per category, min-max scale each team's value to 0–1 (turnovers inverted since lower is better), average the per-category ratings into `avg_rating`, rank teams by that descending. This is what DashApp/Sheets show as "Rating"/"Rank". Confirmed from code, not guessed.

**dashboard_site's current API** (`dashboard_site/api/`):
- `POST /query` — metric + aggregation (sum/avg/min/max/count/rank) + group_by + filters (years/weeks/teams/opponents/seasons/count_only). Good generic ad-hoc slicing.
- `POST /timeseries`, `POST /schedule_swap`, `GET /meta` — supporting endpoints.
- Metric aliasing already covers raw categories + derived matchup/all-play/league/draft metrics (`dashboard_site/api/query_engine.py`).
- `seasons` filter already distinguishes RS vs PO.
- **Gap:** no Weighted Rank / per-category rating-rank, no all-time-leader-per-category helper, no dedicated head-to-head endpoint (approximable today via `teams`+`opponents` filters but not packaged), no records/streaks logic (doesn't exist anywhere yet — best week ever, longest streak, etc.).

**DashApp view shapes** (source of truth for what a "nice" version of these pages should show):
- Weekly view (`DashApp/pages/weekly_stats.py`): year/week/team selectors, focus-team stat row + Rating/Rank, full league table with red/green conditional formatting per category, sorted by week rank.
- Cumulative view (`DashApp/pages/cumulative_stats.py`): Rank column + agg stats table (Team + main categories), Averages/Totals toggle, year/week/team multi-select filters.

**Team identity — resolved.** `Team` in `compStatDF` is the stable member name, drawn from the hardcoded `allMembers` list in `constants.py` (`Jesse, Ange, Juan, Saamrit, Rohil, Chirayu, Fano, Zahir, Amil, Sama, Sai`), not a raw per-season/per-platform team label. `TeamManager` (`Models/TeamManager.py`) is keyed on this name throughout. No mapping table needed for career/profile aggregation across years.

**`fantasyLeague()` instantiation cost.** Building `fantasyLeague()` (all 8 seasons, 2019–2026) takes ~10s locally, no network calls (pure CSV read via `leagueSeason`/`TeamManager`). Fine as a one-time singleton at API startup (same pattern as `StatsStore()` in `dashboard_site/api/app.py`), not per-request.

**Environment wrinkle (RESOLVED in session 3, re-verified in session 4): dashboard_site no longer needs the root venv.** Originally, reusing `Models/League.py` directly meant importing `constants.py` (builds a `gspread` client at import time) and `Models/seasons.py`/`Draft.py`/`Matchup.py` (import `espn_fr`/`yfpy_fr`), plus `scikit-learn`. Session 3 removed this coupling entirely — see "Session 3: decoupling dashboard_site from Models.League" below. dashboard_site's `league_store.py` now has its own independent implementation and only needs `shared/weighted_rank.py` (pure pandas/numpy) plus a small precomputed CSV lookup. Session 4 confirmed the lightweight `.venv-dashboard` (just `dashboard_site/requirements.txt`, no scikit-learn/gspread/espn_fr/yfpy_fr) boots the API and serves all 8 `/league/*` endpoints correctly with zero `Models`/`constants` imports.

**Data-quality flag observed:** `/league/records` surfaced a single-week TO (turnover) record of 0.0 (Zahir, 2019 week 20, marked `real_matchup=1`/`Count=True`/RS). This is very likely a data artifact from that season's export rather than a real 0-turnover week — flagged here per the original plan's Phase 0 point about data quality issues, not fixed (out of scope for the API layer). Worth a manual look before surfacing single-week category records in the UI.

## Session 3: decoupling dashboard_site from Models.League (2026-08-09)

Started from a simple question — "can dashboard_site stay on a lightweight venv?" — and turned into a real refactor plus a genuine production bug fix. Full account below since this is dense enough that a fresh session needs the actual reasoning, not just the diff.

### What changed

1. **`shared/weighted_rank.py` (NEW).** Extracted both Weighted Rank formulas into a dependency-free module (pure pandas/numpy, no scikit-learn — minmax is 3 lines, sklearn was overkill):
   - `per_week_rating(df, main_cats, neg_cats, team_count)` — the per-week formula from `Models/seasons.py::df_build_out` (double minmax: scale each category within the week, average, minmax the average again). Produces `week_rating`/`week_rank` plus per-category `_rank`/`_wt_rank`/`_rating`.
   - `aggregate_rating(df, main_cats, neg_cats)` — the simpler career/season formula from `Models/League.py::get_totals_df`/`get_avg_df` (single minmax, no per-week grouping). Produces `avg_rating`/`Rank`.
   - These are **two different formulas**, not one — don't conflate them if touching this again.

2. **`Models/seasons.py` and `Models/League.py` refactored to call the shared module** instead of inlining the math. Verified byte-identical output before/after (`pd.testing.assert_frame_equal` on `get_filtered_df()`/`get_totals_df()`/`get_avg_df()`, full history) — pure extraction, no behavior change from this step alone.

3. **Real bug found and fixed in `Models/seasons.py::_apply_playoff_count_flags`** (called from `run_playoffs()`). This is production code the live Discord bot and GDoc updater depend on — found while chasing why dashboard_site's playoff-week data didn't match. **Root cause:** the function zeroed out `real_matchup`/`Count` for any team not in the *final* top-4 standings, applied blanket across *all* playoff weeks — including the very elimination-round game that determined they weren't top-4. So a team's real, played elimination game (e.g. the week-19 play-in round) got wiped, and since the mask also checked the *opponent*, it wiped the winner's row too (their opponent was the just-eliminated team). This silently dropped week-19 entirely for any season where the play-in-round loser detection actually worked (2024, 2025, 2026 — confirmed via testing that 2022/2023 were *accidentally* unaffected because loser detection happened to return nothing there, an artifact of `is_WL`/`is_espn` differences between older ESPN seasons and newer Yahoo ones, not because the bug didn't apply).
   - **Fix:** track `self.elim_week[team] = week` at the point of elimination; only exclude a team's rows for PO weeks *strictly after* their elimination week, never the elimination week itself.
   - **Verified via user's own domain knowledge**: confirmed 2022/2024 (and by extension 2025/2026) really do use a 6-team bracket with the top 2 seeds getting a week-1 bye — this was the detail that led to finding the bug in the first place. 2019/2021 (4-team bracket, no byes) and 2022/2023 correctly unaffected.
   - **Verified impact scope:** diffed `get_filtered_df()`/`get_totals_df()`/`get_avg_df()` before vs. after — exactly 12 new rows appear (4 teams × 3 years: 2024, 2025, 2026 week-19 play-in games), zero rows dropped anywhere. The widespread ripple in `_rating` columns across *unrelated* teams is expected and correct (minmax scaling is relative to the whole league's range that category — adding real data for the affected teams shifts everyone's rating slightly).
   - This fix changes real output for 2024/2025/2026 playoff standings/totals. **GDoc and the Discord bot will see different numbers for these years once they next run** (in a good way — this is a correctness fix) — worth a heads up to Ange/whoever if playoff results for those years get referenced/shared before this is deployed there.

4. **`scripts/export_real_matchup_flags.py` (NEW).** dashboard_site still needs to know which playoff-week teams are in the real bracket vs. a consolation ladder (the raw CSV's `Count` flag doesn't distinguish these — see the original finding below), but re-deriving that seeding/standings logic independently in the lightweight path would risk a fresh version of the bug just fixed above. Instead: this script runs `fantasyLeague()` (full venv, has the now-correct logic) and exports a tiny `(Year, Week, Season, Team) -> real_matchup` lookup to `Ref/real_matchup_flags.csv` (76 rows, playoff weeks only — regular season doesn't need this, `Count` is reliable there).
   - **Must be re-run whenever `Ref/*_CompStats.csv` changes**, same cadence as whatever already refreshes GDoc/stats. **Not yet wired into `deploy/scripts/`** — that's a remaining TODO.
   - Gotcha already hit once: the first version used `.drop_duplicates()` on `get_filtered_df(real=False)` output, which has multiple rows per team per week (one real, several hypothetical all-play comparisons) — `drop_duplicates` kept an arbitrary one. Fixed by `.groupby(...)["real_matchup"].max()` instead (logical OR across the group).

5. **`dashboard_site/api/league_store.py` rewritten** to not import `Models.League`/`constants` at all — uses `StatsStore`'s own CSV-loaded data (`dashboard_site/api/query_engine.py`) plus `shared/weighted_rank.py` plus the precomputed lookup from step 4. One subtlety worth preserving in comments (already is, in the code): the per-week rating calculation (`_ensure_rated_df`) must use the *broader* `Count==True` universe as its comparison pool, not the stricter bracket-only mask — because `Models/seasons.py::df_build_out` computes ratings *before* its own playoff-bracket filtering runs, so a playoff week's rating is genuinely calculated against everyone who played a real game that week (bracket + consolation alike). Narrowing the pool changes the numbers even for bracket teams, since rank/rating are relative. The bracket-aware mask (`_real_matchup_mask`, backed by the step-4 lookup) is applied separately, only to decide which *rows* get surfaced/aggregated (`_filtered_raw`, the matchup pairing in `_ensure_weekly_df`).
   - `app.py` updated: `get_league_store(store)` now takes the already-loaded `StatsStore` instance instead of building its own (avoids loading the CSVs twice).

### Original finding that started this (still true, now handled)

The raw CompStats CSVs mark `Count=True` for *any* team with a real (non-bye) opponent that week — including consolation-bracket games during playoff weeks. `StatGenerator.py:194` confirms this is deliberate/correct at that layer (`count = False if Opp == 'BYE' else True`) — it's a faithful raw capture, not a bug. Regenerating the CSVs to drop consolation-bracket rows would be a real data-loss regression and would wrongly push season-structure knowledge into what should be a dumb capture layer. The right fix is knowing which teams are in the real bracket (seeding/standings-derived business logic that already lives in `poSeason`), which is what steps 4–5 above provide without re-deriving that logic twice.

### Verification status — RESOLVED in session 4

Compared dashboard_site's `LeagueStore._ensure_weekly_df()` against `Models.League().get_filtered_df()` (the authoritative ground truth) across `week_rating`, `week_rank`, `cat_wins/losses/ties`, `matchup_win/loss/tie`, full 8-season history (1,438 raw rows / 1,424 deduped keys). **0 mismatches across all 1,424 rows and all 8 compared columns** (previously 18 mismatched `week_rank` rows, see below).

**Root cause of the original 18: a genuine duplicate block in the raw source file**, not a code bug. `Ref/2025_CompStats.csv` had the entire week-20 PO block for 3 of that week's 5 matchups (Fano/Saamrit, Zahir/Ange, Chirayu/Juan — 6 rows) recorded **twice**, identical stats, `Count=TRUE` vs `Count=True` (the casing difference suggests a re-run/append in the stat pipeline). The other 2 matchups that week (Amil/Sama, Sai/Rohil) were unaffected — confirmed by checking all years for this pattern (`df.duplicated(subset=all_cols_except_Count, keep=False)` per year): only 2025 week 20 PO was affected, nowhere else across 2019–2026. `Models.League`'s dict-keyed `statDict[week][team]` structure naturally collapses this (last write wins), so it never showed up there; dashboard_site's CSV-row-based matchup pairing didn't dedupe, so the duplicate produced a 2×2 cross-product in the reciprocal join, throwing off `.rank()` (not `.rating`, which is unaffected by row *count*, just values).

**Fixed**: added `all_df.drop_duplicates(ignore_index=True)` to `StatsStore._load_all_compstats` (`dashboard_site/api/query_engine.py`), after Count-column normalization so the `TRUE`/`True` casing difference doesn't block the match. Chose the loader-level fix over hand-editing the CSV — mirrors the protection `Models.League`'s dict structure already gets for free, and guards against a future pipeline re-run producing the same class of duplicate in any year/week without needing another manual CSV edit. The raw CSV itself is untouched (still a faithful, if occasionally duplicated, capture layer).
